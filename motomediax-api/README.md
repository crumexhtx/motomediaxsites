# motomediax-api

A small Express JSON API over the MotoMediaX vehicle catalog (makes → models
→ years, specs sourced from NHTSA/EPA/Wikipedia), extended with NHTSA recall
and owner-complaint data per model year.

This is a standalone Node project living inside the `motomediaxsites` repo
alongside the Next.js site — it has its own `package.json`/`node_modules`
(plain `npm`, not part of the site's pnpm workspace) and isn't deployed by
the site's build.

## Setup

```bash
cd motomediax-api
npm install
npm run build:catalog          # generates data/catalog.json from the sibling site's catalog
npm run seed:recalls-from-site # one-time bootstrap — see "Data provenance" below
npm start                       # http://localhost:3001
```

## Endpoints

- `GET /v1/health` — catalog size + how many vehicles have safety data
- `GET /v1/makes` — all makes
- `GET /v1/makes/:makeSlug` — a make and its models
- `GET /v1/makes/:makeSlug/models/:modelSlug` — a model and its years
- `GET /v1/makes/:makeSlug/models/:modelSlug/years/:year` — full year detail
  (summary, specs, performance/trims, sources), plus a `recallSummary` block
  (`totalRecalls`, `totalComplaints`, `mostComplainedCategory`,
  `recallDataAvailable`, `complaintDataAvailable`) so callers get a signal
  without a second request
- `GET /v1/makes/:makeSlug/models/:modelSlug/years/:year/recalls` — the full
  recall list and complaint-category breakdown for that vehicle

Unknown makes/models/years/routes return `404 { "error": "..." }`.

Existing catalog endpoints are unaffected for vehicles with no recall data —
`recallDataAvailable`/`complaintDataAvailable` are simply `false` with an
explanatory error, never a fabricated empty-looking result.

## Data files

- `data/catalog.json` — generated by `scripts/build-catalog-from-site.mjs`
  from `../src/data/catalog.generated.json`. Re-run that script whenever the
  site's catalog changes.
- `data/recalls-complaints.json` — keyed by `{makeSlug}/{modelSlug}/{year}`.
  Each record distinguishes three states per data source (recalls,
  complaints), never conflating them:
  - `{ recallDataAvailable: true, recalls: [...] }` — real recall(s) found
  - `{ recallDataAvailable: true, recalls: [] }` — request succeeded,
    **confirmed zero** recalls
  - `{ recallDataAvailable: false, recallsError: "..." }` — the request
    itself **failed**; this is not the same as zero and must not be read as
    "no recalls"

  Same shape for `complaintDataAvailable` / `complaints` /
  `complaintsError`.

## Refreshing recall/complaint data

```bash
npm run enrich:recalls                                # fetch everything not yet fetched
node scripts/enrich-recalls-complaints.js --force      # refetch everything
node scripts/enrich-recalls-complaints.js --brand ford --model mustang-mach-e
node scripts/enrich-recalls-complaints.js --limit 20 --dry-run
node scripts/enrich-recalls-complaints.js --delay-ms 1500   # even gentler pacing
node scripts/enrich-recalls-complaints.js --retries 5        # more attempts per request
node scripts/enrich-recalls-complaints.js --retry-failed     # re-process only ERROR vehicles
```

The script queries NHTSA's public, keyless APIs:

- `https://api.nhtsa.gov/recalls/recallsByVehicle?make=&model=&modelYear=`
- `https://api.nhtsa.gov/complaints/complaintsByVehicle?make=&model=&modelYear=`

NHTSA does not publish a documented rate limit for these endpoints, but in
practice they return intermittent HTTP 400s under load — observed across
both simple and multi-word model names, so it's rate limiting, not a
request-format bug. Requests are serialized (no concurrency) with a delay
between every call (`--delay-ms`, default **750ms**), and each request gets
up to `--retries` attempts (default **3**) with exponential backoff between
retries (500ms, 1000ms, ...) before it's marked failed. A request is only
ever reported `FETCH FAILED` after every attempt has failed — never after
just one.

`--retry-failed` re-processes only vehicles whose stored record currently
has `recallDataAvailable: false` or `complaintDataAvailable: false`; it
skips vehicles that were never fetched at all (that's what a plain run or
`--force` is for) and, within a vehicle, only refetches the data source
that actually failed — a vehicle whose recalls errored but complaints
succeeded won't re-request complaints. `--force` and `--retry-failed` are
mutually exclusive.

It prints a summary at the end — vehicles processed, and an `ok` /
`confirmed empty` / `reused` (skipped because it already had good data) /
**`FETCH FAILED`** count for each of recalls and complaints, so failures
stay visible rather than silently rolled into the empty count.

Known limitation: the script queries NHTSA using the catalog's model name
as-is (e.g. "Mustang Mach-E"). It does not do the fuzzy make/model-name
resolution the main site's `scripts/nhtsa-safety.ts` does (an extra
`/products/vehicle/models` lookup per make/year to match catalog names to
NHTSA's exact model strings). For most mainstream models this matches fine;
for edge cases you may see spuriously empty results if NHTSA's model string
differs meaningfully from the catalog's.

## Data provenance for the initial `recalls-complaints.json`

The sandbox this API was built in cannot reach `api.nhtsa.gov` (outbound
network policy blocks it — confirmed via a direct CONNECT attempt, not
assumed). So `data/recalls-complaints.json` was **not** generated by
`enrich-recalls-complaints.js` in this environment. Instead,
`scripts/seed-recalls-from-site.mjs` bootstrapped it from real NHTSA data
the sibling Next.js site had already fetched (`src/data/catalog.generated.json`
`year.recalls` / `year.complaints` / `year.safetyStatus`, populated by that
repo's own `pnpm enrich:nhtsa-recalls` run) — genuine records, not
fabricated or estimated.

While importing that data, a date bug was found and fixed: the site's
fetcher (`scripts/nhtsa-safety.ts`) assumes NHTSA returns dates as
DD/MM/YYYY and stores them as `YYYY-DD-MM`. NHTSA actually returns US-style
`MM/DD/YYYY`, so any recall reported on the 13th–31st of a month came out
with an invalid month component (for example `"2026-30-06"` — month "30").
`seed-recalls-from-site.mjs` repairs this on import (swaps the two
components back whenever the "month" position is > 12), and
`enrich-recalls-complaints.js` parses dates as `MM/DD/YYYY` correctly from
the start. This bug is upstream, in the main site's repo, not in this API
folder — worth a fix there too.

## Validation performed

- Automated: `npm test` (`test/server.test.js`) covers every endpoint,
  the merged-summary shape, 404s, and — using the two real cases already
  present in the seeded data — that a confirmed-zero-recalls vehicle
  (Toyota Supra 2026) and a genuinely failed fetch (Tesla Model 3 2024,
  NHTSA recalls endpoint returned HTTP 500 during the site's own fetch) are
  represented distinctly, not collapsed into the same "no recalls" shape.
- Manual: started the server and hit
  `/v1/makes/ford/models/mustang-mach-e/years/2024/recalls` — returns 11 real
  recalls (e.g. campaign `26V418000`, a windshield-wiper recall) plus a
  72-complaint summary topped by "Electrical System".
- **Not performed, and you should before trusting this data**: cross-checking
  recall counts/campaign numbers directly against nhtsa.gov. This sandbox's
  network policy blocks that lookup the same way it blocks the live
  enrichment fetch — see "Data provenance" above. Spot-check a handful of
  campaign numbers (e.g. `26V418000`, `25V546000` for the Mach-E) against
  NHTSA's own site before relying on this for anything user-facing.
